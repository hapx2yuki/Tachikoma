# 組立手順 (脚 1 本 → ベンチ試験 → 全体 → 腕) — 2026-07 レビュー反映版

**2026-09-05 第2次監査:** この手順の旧合格記録は製作許可を意味しない。現在は足の嵌合/支持、頭内収納と固定、ポッド梁に未解決項目がある。
先に[最新監査](audits/20260905-round2/README.md)と[部品別の変更](audits/20260905-round2/manufacturing.md)を確認する。既存3MFは保存してあり、修正済みSTLとの不一致を含む。

関節は全て**ホーン片持ち結合** (アイドラーネジは廃止)。脚サーボは全軸
DS3218 級 (出力軸デュアルベアリング必須)、腕は MG90S ×3/腕 (肩ヨー/肩ピッチ/肘。
2026-07-29 固定爪化でグリップ用サブマイクロは腕から廃止済み — §2.5 参照)、
目はサブマイクロ ×2 (左右キョロキョロ, §2.7)。

**ガード・固定爪の接着前に必要な改訂:** 大腿/脛ガードは体積の81%/78%が支持殻に埋まり、26方向の候補でも受け座へ挿入できなかった（RV-16）。固定爪は指・指飾りを含む36組中10組に交差があり、公差/圧入仕様が未確認（RV-17）。下記の古いembed率と「現物合わせ」は組立成立の根拠にならない。

## 0. 事前準備

**タッピングねじの扱い (全工程共通)**: M3×10 / M2.6×8 / M2×8 / M1.7 のセルフタップは
印刷ボス (PETG/PLA, 下穴 φ2.8/φ2.2/φ1.6/φ1.1) へ直接ねじ込む。**低速・低トルクで、
手応えが急に軽くなったら (空転/白化) 増し締めせず一旦抜いて入れ直す**。締めすぎると
ボスが割れる (肉厚は `check_screw_bosses.py` で 70% 以上を保証しているが、トルク超過には
耐えない)。電動ドライバは使わない。同じ穴への抜き差しは 3 回までを目安に。
膝/股/ヨーホーンの共締め M2.6 は下穴 φ2.2 (`HORN_PILOT_D`, 2026-09-04 に 2.0→2.2。印刷済み
coxa/femur は φ2.2 ドリルで追加工可)。tibia 側は外側増厚部を貫通して 6mm 掛かる。

1. サーボとホーンをノギスで実測 → `hardware/src/config.py` の
   [要実測] 値 (STD / MICRO / SUBMICRO プロファイルと HORN_*) を更新
2. `cd hardware/src && ../../.venv/bin/python build_all.py` で STL 再生成。
   **`Head_Top_Eyecut.stl` はこのコマンドの対象外** (独立スクリプト) —
   `EYE_BORE_D`/`EYE_SOCKETS_150` 等の目ソケット関連値を変更した場合は
   リポジトリルートから `.venv/bin/python tools/make_head_eyecut.py` も
   別途実行して再生成すること (`docs/print_manifest.md` 参照)
3. `AGENTS.md`記載の全検証と`docs/audits/20260905-round2/`の追加検証を再実行する。
   旧7本だけでは、組立挿入経路、部品同士の自己干渉、実際の足底接触を検出できなかった。
4. テスト印刷: coxa_bracket / femur_link / tibia_link / leg_foot_bored /
   foot_pad 各 1

## 1. 脚 1 本の組立 (Go/No-Go 判定)

1. **サーボを中立へ**: 組付け前に必ず全サーボへ 1500µs を与えて中立化
   (ファームの `CALIBRATION_MODE` ビルドを使用)。**あわせて可動端の確認**:
   `CALIBRATION_MODE` ビルドは起動後に全 ch を 1500µs で保持するが、同ビルドの
   `/cal?us=...` (Web UI) でメーカーの許容パルス範囲内を中立から少しずつ広げ、ホーンを
   仮付けして **1500→500 / 1500→2500 の振れ角が ±90° (計 180°) か分度器で目視**する。
   270° 品 (市場で 180°/270° 表記が混在, shopping.md) が紛れていると振れ角が
   ±135° になり、firmware の 500-2500µs=180° 前提が 1.5 倍狂う — その個体は
   現設定のまま混用しない。`DEG_RANGE`は全軸共通なので、1個に合わせて変えると他の軸もずれる。
   180°品で統一するか、個別の変換を設計・検証してから組み込む
2. 膝サーボを femur_link の箱枠へ +Y 側から挿入、**M3×10 タッピング×4** で
   タブ固定 (ケース底が -Y 側へ突き出るのは仕様。装飾ガードで隠れる)
3. 股ピッチサーボを coxa_bracket の箱枠へ挿入、同様にタブ固定
4. tibia_link の円板ポケットに付属ホーンを埋め、M2.6 タッピングで共締め
   → ホーンをサーボ軸へ (tibia 鉛直下向き = 中立、中心ビスで固定)
5. femur を同様に股ピッチサーボへ (femur 水平 = 中立)
6. leg_foot_bored を tibia 先端ソケットへ差し込み接着 → 隠しポケットへ
   foot_pad (TPU) を圧入接着 (printing.md「足 (Leg_Foot 化)」参照)
7. **ベンチ試験**: coxa をバイスで水平固定し、
   - スイープ動作で干渉・ガタ・ホーン緩みを確認
   - **股ピッチ軸から足先まで水平 155mm** の姿勢 (股ピッチ約 -20°/膝約 +15°) で足先に
     **1.2kg の錘** → 股ピッチ = 1.2×15.5 ≈ **18.6 kgf·cm** を 10 秒保持できること (6V 給電、
     脱調・振動・ホーン滑りなし)。これは `sim_gait.py` [3] の全域最悪 18.5 kgf·cm
     (総重量 3.0kg・実重心 y=-39mm・3/4 点支持静力学, 2026-09-04) と同等の負荷。旧記載
     「1.2kg (40% 負担)」はレバー未指定で試験として不定だった
   - 上の最大負荷は、無負荷・軽い負荷から段階的に増やして到達する試験点。
     保持不能、振動、ホーン滑り、急な電流増大があれば直ちに負荷を下ろす。
     10秒の成功だけで連続運転可能とは判定せず、想定歩行時間の温度・電圧降下もL-02/L-11へ記録する。
   - 保持電流を測定する。旧記載の「期待1.5〜2.2A」「1.5A未満」は未実測で互いに矛盾していたため撤回。
     DS3218メーカー値は5Vでストール1.8A、6.8Vで2.2A。6Vの実力・連続保持能力は実測する。
     **DS3218の上限6.8Vを超える7.4Vへの昇圧は対策に使わない**。
   - 膝ネック増厚部 (tibia 外側 +3mm) に白化・割れなし。装飾トゥを付けた状態なら極端姿勢で
     トゥ先端が foot_pad より先に机へ触れないか観察 (S-04)
   - 電流測定器は定格と許容時間を確認する。SANWA PM7aには電流測定機能がない。
   → **持ち上がらなければ全印刷へ進まない**。型番・試験電圧・レバー長・錘・保持時間・電流・温度を保存する。

メーカーの定格は[DS3218データシート](https://www.dsservo.com/down.asp?id=22)で確認 (2026-09-05)。
購入記録のLD20MG/LD220MGは別製品のため、DS3218の値を流用しない。
USBを使う中立化・書込みは、先にDevKitCへの外部5V線を切り離す (`wiring.md`「USB接続時の給電」)。
本体の通常起動は脱力から「立つ」の明示操作で行い、順次通電が終わるまで支持台で支える。

## 2. シャーシと残り 3 脚

1. ヨーサーボ×4 をシャーシ上面から挿入 (ケース長手は 4 個とも **X 軸平行・
   ボディ中央向き** — v3 はケース向きが脚方位と独立)。タブは**台座ボス
   (高さ3mm) に着座**、M3×10 で固定。ギヤヘッドはプレート下面へ突き出る
2. ヨーホーンを coxa 天板ポケットへ埋めて M2.6 共締め → 各脚を中立姿勢
   でサーボ軸へ固定。**v3 の脚方位は非均等**: FR 15° / FL 165° / RL 210° /
   RR 330° (正面=90°。前脚は正面から±75°、後脚は±120°)。**FR と RL には
   ミラー版パーツ (`_m`) を使う** — 取り違えると 45° ペアの股ピッチサーボ
   同士が干渉して組めない
3. **ポッドネック**: pod_neck 梁をシャーシ後端ブラケットへ M3×4 で共締め。
   TailJoint_Blue コーン (+Ball リング) を梁へ被せ接着 (printing.md 参照)
4. **PCA9685 ×2 スタック (2026-08-22 実装確定 — `config.py` PCA_* 定数が
   唯一の正)**: board0 (0x40, 脚+頭) を中央の縦向きボス (h5) へ M2.5×16
   **M-F スタンドオフ** ×4 でネジ止め (スタンドオフのオス側が board0 の穴を
   通ってボスへセルフタップ = 六角肩が board0 を押さえる) → board1 (0x41,
   腕+目) をスタンドオフ上へ
   M2.5×6 ×4 で固定 (下面 z=26.6)。**配線規約 3 点 (必須)**:
   - サーボプラグ列は両ボードとも **+x (右) 側**へ向ける
   - **board1 (0x41) は南端 (−y 側) 約 4ch を空けて北詰めで配線する**
     (上段はプラグ上端が頭殻クラウンの絞りに接近するため。使用 10ch <
     北詰め 11ch で収まる — `tools/make_head_eyecut.py` 検算 [4] が
     この包絡で頭内クリアランスを担保している)
   - **I2C ヘッダは両ボードとも北端のみ実装** (南端に直立ピンを立てると
     上下段間 16mm を超え、下段では頭の床下帯にも近い)
   プラグの挿抜は **Head_Top を外した状態で行う** (被せた状態で保証される
   のは配線済み状態の恒久包絡のみ)。
   **ESP32 は当面テープ/マジックテープ留め** (2026-08-21: ネジ止めボスは
   後脚ケース開口と干渉し chassis から撤去。さらに 2026-08-22 の Head_Top
   実占有ボクセル場での網羅探索で、**頭内の恒久マウントは全姿勢不成立**と
   確定 — `hardware/src/config.py` ESP32_SLOT のコメント参照。恒久固定は
   頭外への移設が必要でユーザー判断待ち。**歩行実験は頭シェル未装着なので
   テープ留めで支障なし。ただし Head_Top を被せる段では ESP32 を頭外へ
   退避すること** — 頭内にテープ留めできる 58×28 の平面はもう存在しない)。
   UBEC/DC-DC は後方 (±30,-58) に両面テープ、SW+ヒューズは右前 (48,28)
   (ホロー化した Head_Top 内面と 0.11cm³ 重なる見込み — 実装時に数 mm
   内側へ寄せて現物合わせ。`make_head_eyecut.py` 検算 [7] 参照)。
   **バッテリーはプレート下面の battery_cradle** に -Y 側から差し込み、
   ベルクロベルトで固定 (低重心化。コネクタは前向き)。目モジュールの
   サーボ尾と干渉しない配置は現物合わせ
5. 配線は wiring.md 厳守 (**サーボ電源は PCA9685 を経由させない**)
6. 通電順: **サーボ未接続で UBEC 出力 (6V レール) と DC-DC (5V レール) をテスタ実測**
   (UBEC の出力切替ジャンパ/スイッチが 7.4/8.4V 側だとサーボが一斉に壊れる, wiring.md)
   → 6.0±0.2V を確認してからサーボ 1 本 → 全数。全数接続後に立位保持の**バス合計電流**
   も記録する (スイッチ/UBEC 定格の判断材料, L-09/L-10)

## 2.5 腕の組立 (脚のベンチ試験合格後でよい)

腕は歩行の成立に影響しないので、脚と並行または後回しで組み立てられる。
**手は 2026-07-29 にキット準拠の固定爪へ変更済み (可動グリッパは廃止)** —
サーボ・配線を持たない受動パーツなので、調整項目は claw_mount と爪ハブの
接着面 (現物合わせ) のみ。

1. **肩ヨー**: MG90S をシャーシの腕マウント開口 (2026-07-28 実ソケット移設:
   Head_Bottom_Blue 側面ソケット直下, 正面から左右 ±40°, `C.ARM_MOUNT_XY`)
   へ**上から挿入・軸下向き** (脚ヨーと同じ要領)。タブを台座ボスに着座させ
   M2×8 タッピング×2 で固定。ギヤヘッドとホーンはプレート下面側へ出る
2. **肩ブラケット**: サーボ中立 (1500µs) の状態で、shoulder_bracket **上面**の
   ホーンポケットに付属ホーンを埋めて M2.6 共締め → ヨーサーボ軸へ吊り下げ
   (**腕は正面向きでなく放射外向き (正面から40°) = 中立** — 実機ソケットの
   向きに合わせる。組付け時、上腕が Head_Bottom ソケットの開口方向を向く
   ことを目視で確認する)。肩ピッチ用 MG90S をブラケットへタブ固定
3. **上腕**: upper_arm のホーン円板を肩ピッチサーボへ (腕鉛直下向き =
   ピッチ 85° 付近)。肘用 MG90S を upper_arm の箱枠へタブ固定
4. **前腕**: forearm のホーン円板を肘サーボへ (伸ばし = 肘 0°)。
   2026-07-29 固定爪化で FOREARM_LEN 24→16mm に短縮済み
5. **手 (固定爪, キット準拠 — 2026-07-29 可動グリッパから変更)**:
   - claw_mount (PETG, forearm と同色) の背面を forearm の手首面 (平坦端)
     へ接着 [現物合わせ, 瞬間接着剤またはエポキシ]。可動部・配線は無し
   - **Arm_Left_Claw_Grey** (爪ハブ, 150% 印刷 ×2, **両腕とも Left 版を
     使用** — Arm_Right_Claw_Grey は形状が異なる別パーツなので使わない)
     の平坦近位面 (接着面を #400 で軽く粗面化し**エポキシ**推奨 — 瞬着より靱性が高い, 2026-09-04 M-03)を claw_mount 前面へ突き合わせ接着 [現物合わせ, 軽く
     均してから接着]
   - **Arm_Left_Finger_Black_x3** (指, 150% 印刷 ×6 = 3本×2腕, **元キット
     タロン形状のまま無加工**) を爪ハブの 3 本のペグへそれぞれ差込 (圧入+
     接着併用)
   - **Arm_Left_FingerTip_Grey_x3** (指先チップ, 150% 印刷 ×6) を各指の
     根元 (ペグとの接合部, キットの組立方法どおり) へ接着
6. **腕シェル (元キットパーツの被せ)**:
   - arm_pod_upper / arm_pod_lower (元 Arm ポッドのクラムシェル 2 分割) を
     upper_arm を上下から挟むように被せて接着 (ホットボンド推奨=脱着可)。
     肘側下面の大きな開口は**肘窩** (前腕折り畳みの掃引域) なので塞がない。
     上殻ホーン側フランクの小さな開口 (~18×5mm) は骨格ウェブの逃げ
     (元ポッドのリブと同位置) — 気になる場合は Arm_Left/Right_Guard_Grey の
     接着位置で隠す
   - elbow_shell (元 Elbow 球の半殻) は改訂STLの位置で肘サーボのケース底へ合わせる。
     原球中心は肘軸から局所Y=-13.8mm。旧原点配置ではケースへ食い込む。
     欠き底は原球中心から-6mmで、ケース底との設計隙間は0.3mm。接着保持力は現物確認
   - Arm_Left_Guard_Grey / Arm_Right_Guard_Grey (左右別形状の元パーツ,
     各 1, 150% 印刷) をそれぞれの腕のポッド表面へ接着 (任意,
     位置は元キット説明書/実機写真と現物合わせ)
7. **左腕**: *_L パーツで同様に (機構は左右ミラー。ファームがヨーを反転)
8. **ベンチ確認**: `/arm?pose=tuck` → `ready` → `reach` → `wave` を
   順に実行し、各姿勢で干渉・脱調がないこと。爪は固定 (可動なし) — 接着が
   しっかり効いて指がぐらつかないことを確認する
9. **腕可動域の実機確認 (重要)**: 検証は粗近似モデルによる。
   **脚を静止 (立位) にしたまま**腕の全域 (特にヨー ±15° 端 × 脚ヨー大) を
   低速で試し、前脚・coxa とのクリアランスを目視確認してから歩行と併用する

## 2.7 目ポッド (キョロキョロ機構) ×2 (左右)

2026-07-28 設計変更: 中央目は固定カメラ目に置換された (§2.9 参照) ため、
本節は**左右 2 目のみ**を扱う (元キット STL の 3 ソケットのうち中央
(EYE_SOCKETS_150[1]) を除く 2 つ)。

1. **eye_pod のドット穴 3 つを黒く仕上げる** (元キットの目パーツと同じ
   モールド穴。黒塗料の流し込み or 黒フィラメント片の接着。このドット群が
   視線マークになる)
2. サブマイクロサーボを eye_carrier のポケットへ (付属ビス)
3. **ホーンを先に eye_pod へ共締めする**: ポッドを手に持ち、背面ポケットに
   ホーンを埋めて、ホーンのアーム穴 2 個から極小タッピング (BOM #29,
   付属ビス流用可) を下穴へ締める。**ホーン中心ビスは使わない** (ポッドに
   塞がれて締結できない。目は無負荷なので摩擦保持で足りる)。ホーン実穴と
   下穴が合わない場合はホーン穴経由で φ1.2 ドリルで現物開け直し
4. **サーボ中立 (1500µs) でドット群がほぼ真下を向く**スプライン位相を選び、
   眼球+ホーンをサーボ軸へ押し込む (ドット群はキャップ軸から ~45° 偏心して
   おり、サーボが回ると視線が泳ぐ)。位相の残差は Web UI の目トリム (±200µs
   ≈ ±18°) で吸収。抜けが心配なら軸に微量の瞬間接着剤
5. **シェル内側から**眼球のネックを Head_Top の目ソケットのボアへ通し、
   carrier をシェル内側へ接着 [現物合わせ]。前提: Head_Top は
   `hardware/stl/Head_Top_Eyecut.stl` (ソケット底へ **φ30 貫通ボア**加工済み)
   を印刷しておく (printing.md。元の Head_Top はソケット底が塞がっている)。
   キャップ (φ37.7 = 元キットの目パーツと同形状) は座グリ (φ42.3) の中で
   回転し、縁との隙間は片側 ~2.3mm。**キャップ底を座グリ床から ~1.5mm
   浮かせる** (check_eye [5] と同じスタック)。全回転で床・縁に擦らないこと
   を確認
6. **carrier のロール向き**: 3 つのソケット法線は仰角 ~47° で頭部中心下方へ
   収束するため、サーボの尻尾と中央目の camera_carrier が中心付近で近づく。
   **サーボケースの長辺を水平の接線方向** (右目・左目 = 前後方向) に向けて
   接着すること — この向きで左右サーボ尾部間クリアランス 41.9mm、中央
   カメラとの間も 22.6mm 以上を確保 (check_eye [5] で検算)。サーボ線は
   ケース後端から接線方向へ出るので、そのまま横へ逃がしてシャーシ 7 タブ
   間隙間 (`docs/wiring.md` 参照) から胴へ下ろす
7. WS2812 の LED 1・3 (右目・左目) を carrier 裏へ貼ると眼球がバックライト
   される (任意。中央 LED (ch2) は中央目がカメラ化されたため未使用/割愛可)
8. `/eye?mode=kyoro` でキョロキョロ / `front` で正面固定 / `scan` で掃引
   (いずれも左右 2 目のみ動作。中央固定カメラは §2.9 参照)

## 2.8 音声会話ユニット (砲身内蔵マイク+スピーカー)

`docs/voice.md` の音声会話 (STT→LLM→TTS ブリッジ) 用。配線は

## 2.9 頭部中央目カメラ (固定, 左右目はキョロキョロのまま)

`docs/voice.md` §5「カメラ連携」用。**2026-07-28 設計変更**: カメラは
ポッド (Cabin) のメインアイではなく、**頭部の中央可動目を固定カメラ目
(`eye_pod_camera`) に置換したもの**へ内蔵する。左右 2 目はキョロキョロ
(§2.7) のまま。ポッドのメインアイ (`Cabin_Eye_White`) は元パーツのまま
無加工で使う (Cabin 前面の組立はキット標準手順のみでよい)。

**撤去理由 [実測済]**: ポッド前面のメインアイ位置は前方視界の約 80% が
自機体 (シャーシ下面/クレードル) に遮蔽されることが `robot_meshes
(dress=True)` 全アセンブリのレイキャスト検証で判明した。頭部中央目は
シャーシから離れているためこの問題が無い (`tools/check_camera.py` [4] が
恒久チェックする)。

配線は `docs/wiring.md` の「カメラ電源配線」参照。**前提パーツ** (いずれも
`hardware/stl/` に出力済み。`make_camera.py` 生成): `eye_pod_camera_shell` +
`eye_pod_camera_base` (印刷用 2 分割, 2026-08-19 印刷性再設計 — 一体版
`eye_pod_camera` は印刷失敗多発のため分割した。一体版 STL は検証/可視化用
参照形状で印刷しない。形状は元キットの目パーツ Head_Eye_White のまま、
キャップ軸から 38.0° 偏心した位置に瞳ボア φ10mm + モジュール収容キャビティ
を追加加工) / `camera_carrier` (レンズ側の子基板を保持する隠しパーツ。
2026-08-19 短縮 — base のポケットへ先入れする方式になり、旧設計の頭部
シェル接着ウィングは廃止)。加工域以外は元メッシュのまま (鉄則1,
`tools/check_camera.py` [1] で確認済み。分割の整合は同 [5])。

**光軸の向き (重要)**: 中央目ソケットの法線は仰角 ~46.6° (ほぼ真上向き) —
既存のキョロキョロ機構と同じ「ドット群が軸から偏心する」原理を使い、
瞳をキャップ軸から 38.0° 偏心させた位置に開けている。**この偏心方向が
正しい向きでグルーされて初めて光軸が水平前方 (残差 ~8.6°) になる** ため、
取付時の回転位相 (下記手順3) を必ず守ること。完全な水平相殺 (46.6°)は
Head_Eye_White カップの材が薄く、モジュールを収めるだけの肉厚安全代が
取れないため断念した (`config.py` CAM2_THETA_DEG コメント参照)。

**印刷前の検証**: 寸法は BOM #34 のモジュール実寸 (子基板 20.5×12.5×5.54mm)
前提で設計済み。別モジュール (例: BOM #34b の ESP32-CAM は基板一体型で
寸法が大きく異なる) を使う場合や実測が違う場合は `config.py` の
`CAM2_MODULE_*` を更新 → `build_all.py` 再生成 → `check_camera.py` 緑を
確認してから印刷する。

1. **カメラモジュール (レンズ側の子基板) を camera_carrier へ固定**:
   ポケットへ子基板を差し込み、瞬着で軽く固定する (ポケットは実寸+片側
   0.4mm クリアランスの設計)
2. **配線を側方の切り欠きから引き出す**: 電源 (VCC/GND) の AWG30
   シリコン線 2 芯を camera_carrier 側方の配線切り欠きから外へ引き出す
3. **carrier+モジュールを eye_pod_camera_base のポケットへ先入れし、
   shell を被せて接着する (2026-08-19 分割版)**: carrier を base の斜め
   ポケットへ落とし込み (ポケット形状で挿入向きが機械的に一意に決まる —
   誤った回転では入らない)、FPC を base 底面のスロットから引き出す。
   次に eye_pod_camera_shell を上から被せ、base 上面のリングプラグを
   shell 底面の溝へ嵌合させて接着する — 斜めチャネルが carrier を貫く
   ため shell/base の回転位相も一意。光軸仰角の残差 8.6° は要求 ±10° に対し余裕 1.4° しかないので、接着中は机面+スコヤで shell の水平を出す (2026-09-04 M-04)に決まる。レンズ面は瞳の奥 (標準距離
   6.57mm) に自動的に位置する
4. **組み上がったポッドを Head_Top の中央目ソケットへ、正しい取付位相で
   グルーする**: 左右目 (§2.7) と同じ φ30 貫通ボアへネック (φ28, 回転
   しない固定パーツのため左右目よりネック径を太くして接着代を稼いでいる)
   を通し、シェル内側から接着する。**瞳が水平前方をまっすぐ向く姿勢**
   (組み上がった頭部の前後軸に対し瞳が正面・水平になる向き。現物合わせ
   — 簡易な水準器や頭部の前後基準線を使って目視で合わせる。設計上の
   残差は ~8.6° なので多少のズレは許容範囲) でネックを挿して固定する
   (旧設計の camera_carrier 接着ウィングは分割版で廃止済み)
5. **本体基板の設置と配線**: 本体基板 (ESP32S3 チップ/WiFi アンテナ/
   USB-C) は camera_carrier に載せず、FPC で子基板と接続したまま**頭部
   内部の空きスペース**へ現物合わせで固定する (両面テープ等。頭部内で
   完結)。電源 2 芯のみシャーシ 7 タブ間隙間 (頭部は完全固定で可動部が
   ないため、首の回転部を避ける配慮は不要) から胴へ下ろす — 給電元
   (5V/3A DC-DC) と電流収支の注意を含め `docs/wiring.md`
   「カメラ電源配線」参照
6. **検証**: 形状側は `tools/check_camera.py` が緑 ([1] 外殻無傷+光軸自己
   整合 / [2] FOV ケラレ / [3] 収容干渉 / [4] 全アセンブリ視界 / [5] ネック
   /座グリ整合) であることを確認。実機側はカメラを WiFi (iPhone インター
   ネット共有) へ接続し、HTTP で静止画/MJPEG が取得できることを確認する
   (手順は `docs/voice.md` §5 参照。本体の I2C/PCA9685 バスとは無接続の
   ため、既存電装への影響はない)

## 3. 意匠シェル

- shin_shell: tibia へ下からスライド → M3×40×2 本を横から貫通、ナイロン
  ナット留め
- **shin_shell のループ意匠 (2026-07-31 修正、同日中に方針を再修正)**:
  Leg_Shin_Blue_x4 に造形されているリング/ハンドル状の突起 (元キットでは
  機体内側を向く意匠) が `shell_mod.py OFFSETS["shin_rotz"]=90°` の旧設定
  では機体外側を向いてしまっていた (URDF ビューアのスクリーンショットで
  ユーザーが指摘。「内側に向けた上で、動作の邪魔になるなら削ってよい」と
  許可あり)。
  **第一次対応 (同日、後に不十分と判明)**: shin_rotz を 90→270° (+180°)
  へ変更すればループが内側へ反転すると考えたが、これは誤りだった。
  実スタンディング姿勢・実カメラ視点で 0°/90°/180°/270° を総当たり
  再検証したところ、90° でも 270° でもループは "内向き" ではなく機体中心
  から見て半径方向おおよそ 50-65° (依然として外側寄り、"横向き") にしか
  ならず、外側カメラからほぼ同程度に視認できてしまう (90→270 は実質的な
  改善になっていなかった)。真に内側 (半径方向 176° 程度、ほぼ機体中心を
  指す) を向く角度は shin_rotz≈0° 近辺のみだったが、この角度では脚の
  断面の「厚い側」が隣接脚 (45°ペア, 例 FR-RR) の方向へ向くことになり、
  両脚を firmware の許す最大内寄せヨー+深屈み (pitch45°/knee30°) へ
  同時に取らせると shin_shell 同士が 7-9cm³ も交差する新規の重大干渉が
  発生した。この干渉はシェルの下半分〜中盤 (Z方向85mm超) にわたる面での
  接触であり、局所リリーフでは対応できない規模 (シェル片側の壁をほぼ全長
  にわたり削り取ることになり、ユーザー許可の「飛び出している部分」の
  trim の範囲を明らかに超える) と判断し、Z 回転による "隠す" 対応は
  断念した。
  **最終対応**: ループ/ハンドルの意匠そのものを、raw メッシュ座標に固定
  した位置で直接切除する (`shell_mod.py` `LOOP_RELIEF_*`, shin_rotz の
  回転より前段で適用するため角度に依存しない)。どの角度から見てもループ
  は存在しないため、外側から見えないというユーザー要求を回転よりも確実に
  満たす。これにより shin_rotz は再び自由なパラメータに戻ったため、270°
  を維持: 45°ペア隣接脚干渉が (KNEE_RELIEF/TIP_RELIEF 込みで) ほぼゼロに
  収まる角度帯 (実測で概ね 240°-315°) の中にあり、90° 近辺 (旧来値) は
  同じ隣接脚干渉が 25-30cm³ という致命的な規模になる、今回判明した
  未発見の既存不具合だった (今まで check_leg_assembly.py が shin_shell を
  一度も隣接脚検査に含めていなかったため発覚しなかった。90°/270° は
  カット形状が原点対称という意味では等価でも、干渉相手 (隣接脚) との
  位置関係は回転で大きく変わるため、隣接脚干渉量には全く等価ではない)。
  向き変更・意匠切除後、可動域全域の実メッシュブーリアン再検証で以下が
  判明し、`shell_mod.py` に局所リリーフカットを追加して解消済み:
  (1) **KNEE_RELIEF**: 深い股ピッチ+膝屈曲 (pitch≥35°, knee≥35° 目安) で
  shin_shell (ループとは無関係の別部位) が femur_link (+膝サーボ) と交差
  (無対策で 0.22-0.26cm³。ループの有無・shin_rotz の値によらず存在する
  既存不具合と判明) → T_knee ローカルの該当領域を丸めボックスで除去
  (→0.00cm³, femur/coxa 双方・pitch/knee全域・sim_gait 実歩容192姿勢で
  再検証済み)。
  (2) **TIP_RELIEF**: 隣接脚遠ペア (FR-FL/RL-RR) が両者フルヨー±40°+
  深屈み (pitch45°/knee30°) のときだけシェル下端外縁同士がごく僅かに接触
  (0.0103cm³) → 同様に小さなリリーフカットで解消 (→0.00cm³)。
  **→ 2026-07-31 別タスク「shin_shell のリリーフカット再評価」で両カットとも
  撤去済み** (本節末尾参照) — shin_rotz=0 の現行形状では KNEE_RELIEF の

  `ARM_MOUNT_HUB_Y` を 12→0 (完全中央) にした際、肩ヨー軸が旧 y≈49.8mm→
  y≈37.8mm へ 12mm 体幹側 (前脚側) へ後退し、旧ゲート `20°` では新形状で
  無対策1.47cm³の干渉を残す状態になったため、一時的に `ARM_LEG_YAW_GATE_
  DEG=10°` へ引き下げていた (中立姿勢9.12°との margin はわずか0.88°で
  発火率70-74%という運用上望ましくない状態だった)。(2) その後「境界
  スイープ (実現可能な最中央値確定)」タスクで `hub_y=0` は
  `check_screw_bosses.py`/`check_arm.py` の静的検査で NG (物理的に不可能)
  と判明し、実測スイープにより `hub_y=11.0` (旧12.0から1mmだけ中央寄せ)
  を採用した (§3「境界スイープによる解決」参照)。この結果、肩ヨー軸の
  後退量が y≈37.8mm→y≈48.77mm (hub_y=0時からほぼ12mm回復、旧12.0時代
  とほぼ同じ配置) となり、gate も再度導出し直す必要が生じた。
  以下は `hub_y=11.0` 確定後に `scratchpad/onset_scan.py`
  (leg reachable集合83点×腕yaw/pitch/elbow全域126点の総当り) で
  2026-07-31 に実測・確認した最終根拠:
  - FR の中立 (静止立位) leg-local yaw は `sim_gait.leg_ik()` 実測で
    約 +9.12° (`hub_y` に非依存の脚側パラメータのみで決まるため不変)
  - クランプ非発火時 (腕 yaw/pitch/elbow 全域, 脚 pitch/knee 到達可能集合
    全域) の shin_shell 干渉は、hub_y=11.0 では FR yaw=17.5°まで常に
    0.0000cm³ (中立姿勢9.12°を含め大きな安全マージンあり)、yaw=20.0°で
    0.0023cm³ (実質ゼロ)、yaw=25.0°で1.3305cm³、yaw=30°で4.8404cm³ —
    onset (0.01cm³しきい値の二分探索) は **20.03°**。比較として
    hub_y=0.0 では同じ手法で onset=**11.00°** (旧「10-12.5°」という粗い
    見積りと整合) だった。**新ゲート `ARM_LEG_YAW_GATE_DEG=20.0°`**
    (onset直下, 旧`hub_y=12.0`時代と同じ値) は中立姿勢9.12°との margin
    **10.88°** を確保する (旧hub_y=0/gate=10°時代のmargin 0.88°から
    大幅に改善)
  - 腕側の退避は従来どおりヨーだけで足りる (pitch/elbow は無関係)。
    `check_shin_arm_leg.py` [C]/[C-duty] の実チェッカーで新ゲート適用後の
    全域グリッドがceiling(0.25cm³)内に収まることを確認済み (PASS, 詳細は
    下記発火頻度パラグラフのチェッカー実行結果参照)
  - FL(左脚)+左腕は FR+右腕の左右鏡像 (shin_shell/腕とも X ミラー構成) で、
    数値が厳密に一致する (危険方向の yaw 符号だけが反転,
    `ARM_LEG_YAW_SIGN={+1,-1}`, 変更なし)
  実装: `firmware/src/arms.h` の `Arms::update()` が呼び出し側 (`main.cpp`)
  から当該フレームの前脚関節角 (`legAng[0]`=FR相当, `[1]`=FL相当) を受け取り、
  同側脚が危険域なら腕ヨーを target/cur_ (スルーレート後) の両方で
  `-ARM_YAW_LIM` へ強制する (「目標側だけのクランプは独立スルー軸がある
  遷移で必ず破れる」という本プロジェクト既知の教訓に従い2段で適用)。
  検証: `tools/check_shin_arm_leg.py` [C] を拡張し、firmware のクランプ式を
  config.h から regex 読取で複製した上で、クランプ通過後に到達可能な
  全姿勢集合 (FR脚 yaw全域×pitch/knee 到達可能集合×腕 pitch/elbow 全域,
  危険域のみ) で実メッシュ干渉が0.25cm³ (既知許容残留 0.166cm³ に余裕を
  持たせた ceiling) 未満であることを確認済み (PASS)。**再導出タスクで
  [C] の全域グリッド判定も [B] (shin-shin/tibia-tibia) と同じ
  `pk_reachable()` (firmware到達可能集合) 基準に統一した** — 旧判定は
  (leg_pitch,leg_knee) を絞り込まずに評価しており、gait.h ワークスペース
  射影の不動点条件を満たさず歩容コマンドとして出力され得ない組合せ
  (worst=0.8546cm³) を誤って算入していたため。Web UI は腕ヨースライダーの
  範囲が既に ±15° (=`ARM_YAW_LIM`) と一致しており、クランプ発火時に
  スライダー値自体を書き換える必要はない (地面ガード等の既存クランプと
  同じ「無言で出力だけ retreat する」挙動を踏襲、UI側の追随実装は不要と
  判断)。
  **クランプの発火頻度 (2026-07-31 境界スイープタスクで最終確定, 詳細は
  §4)**: `hub_y=11.0`/ゲート20.0°の組合せで `tools/check_shin_arm_leg.py`
  [C-duty] を本節作成セッションで実際に再実行し、通常の前進歩行中
  (前進速度 vx=0.1〜1.0, 各600サンプル) に発火する時間比率を実測した結果
  **42.5%〜44.2%** (ほぼ速度非依存) だった (**2026-09-04 の重心対応スタンス STANCE_OFF_Y -30 後は
  0%〜12.7% で速度依存** — 低速ではほぼ発火せず最大速度で 12.7%。監視レンジは「最大速度で 25% 未満」に変更) — 中間段階の
  `hub_y=0`/ゲート10°時代の70-74%から大幅に低下し、旧`hub_y=12.0`時代の
  42-44%相当の水準にほぼ完全に復帰した (肩ヨー軸の後退量が
  hub_y=0時のほぼ12mmからhub_y=11.0では実質1mm相当まで縮小したことの
  直接的な帰結)。歩容周期 `CYCLE_T=1.6秒` のうち約0.68〜0.71秒が該当し、
  「前方へ大きく振れる瞬間限定」という従来の説明が改めて妥当になった。
  `tools/check_shin_arm_leg.py` [C-duty] がこの発火時間比率を毎回実測・
  回帰監視する (想定レンジは42-44%近辺へ復帰、下記§4の表も参照)。

## 4. 歩行調整

1. Web UI の Trim 画面で脚 13ch + 腕 8ch + 目 2ch (左右のみ。中央は固定
   カメラ目でサーボ無し) のセンター微調整 (足先が正方形の四隅、腕は
   TUCK 姿勢で左右対称、目は瞳が真下)
2. 逆に動く関節があれば `config.h` の `JOINT_SIGN` (脚) / `ARM_SIGN` (腕) の
   該当エントリを反転 (v3: FR/RL はミラー脚なのでピッチ/膝の初期値が -1。
   標準脚 FL/RR と鏡向きに動くのが正しい)
3. 体高 115mm・歩幅 50% から開始、安定したら上げる。歩行中の腕は TUCK 推奨
   (肩ピッチに ±8° のスイングが自動で乗る)
4. フローリングで滑る場合は foot_pad (TPU) の硬度/接地径を調整
