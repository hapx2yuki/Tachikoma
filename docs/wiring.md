## 電源系統

```
2S LiPo 7.4V ─[15Aヒューズ]─[ロッカーSW]─┬─ UBEC 6V/10A ══(AWG16)══→ サーボ電源バス
 (2200mAh 35C, XT60)                      │        └ 1000µF×2 をバス直近に並列
                                          └─ DC-DC 5V/3A ──→ ESP32 VIN / DFPlayer
                                                   └ 470µF     / 74AHCT125 / WS2812 5V
```

重要 (レビュー指摘の反映):

- **サーボ電源は PCA9685 の V+ 端子台に集約しない。** 12× 20kg サーボの合成電流
  (歩行時 4〜8A、突入はさらに上) は基板パターンの定格を超える。
  → サーボ延長ハーネスの電源線を **AWG16 の電源バスバー (または太線ハブ)** に
  直結し、PCA9685 へは信号線 + GND のみ接続する (V+ 端子は未接続または
  コンデンサ専用)。GND は全系統共通。
- **腕サーボ (MG90S ×6 + サブマイクロ ×2) も同じ 6V バスから給電**する
  (合計 ~1A 級で余裕内)。サブマイクロは 6V 耐圧品 (ES9251II 等) を使うこと。
  電流が小さいので腕 8ch は board1 (0x41) の V+ 端子台経由でもよいが、
  バス直結に統一する方が配線が単純。
- ロジック 5V は 3A 級。ESP32 (WiFi ピーク ~0.5A) + WS2812 12 灯 (最大 ~0.7A)
  + DFPlayer/スピーカー (~0.5A) が同居するため 1A 級では不足する。
- 低電圧保護はファームに実装済み (6.8V 警告 / 6.4V×3 秒で自動脱力)。

## PCA9685 チャンネル割当 (firmware/src/config.h の PCA_CH / ARM_CH と一致)

PCA9685 は **2 枚**: board0 = 0x40 (脚+頭)、board1 = 0x41 (腕)。
**board1 はアドレスジャンパ A0 をハンダブリッジ**して 0x41 にする。
ファーム内のグローバル ch = board×16 + ローカル ch (例: グローバル 17 =
board1 のローカル ch1)。

| 2 | FR 膝 | 8 | RL 膝 |

| 4 | FL 股ピッチ | 10 | RR 股ピッチ |
| 5 | FL 膝 | 11 | RR 膝 |
| 12 | 頭部ヨー | 13-15 | (予備) |

### スタック実装の向きルール (2026-08-22, Head_Top 内部逃がしとセットで確定)

Head_Top (内殻ホロー化済み) の頭内クリアランスは以下の実装規約を前提に
検証されている (`tools/make_head_eyecut.py` 検算 [4], `config.py` PCA_*):

- **board0 (0x40) = 下段** (ボス直上 z=9)、**board1 (0x41) = 上段**
  (M2.5×16 スタンドオフ, z=26.6)。サーボプラグ列は**両ボードとも +x (右) 側**
- **両ボードとも ch0 側を北 (+y, 頭正面側) に向けて取り付ける**。これで
  上段 board1 の未使用チャネル (ローカル 11-15) が南端に集まり、使用
  チャネル (0-10 = 腕 6 + 目 2 + 予備穴) が北詰めになる — 上段南端の
  プラグ上端は頭殻クラウンの絞りと干渉するため、**上段の南端 ~4ch には
  プラグを挿さないこと** (firmware 側の割当は変更不要 — 11-15 は元々未使用)
- **I2C ヘッダは両ボードとも北端のみ実装** (南端の直立ピンは上下段間/
  頭床下帯に収まらない)
- プラグの挿抜は Head_Top を外して行う (被せた状態で保証されるのは
  配線済み状態の包絡のみ)

FR=右前, FL=左前, RL=左後, RR=右後 (前=+Y)。右腕=+X 側。
目サーボ線は頭部からシャーシ周囲の 7 タブ間隙間 (下記「配線連通の悉皆確認」
#6 参照) を通って胴へ下ろす。頭部は完全固定 (assembly.md §3, 可動部なし) の
ため、ケーブルが可動関節をまたぐ区間はない — 「頭部ヨー ±25°」は CH_HEAD
(ch12) の firmware 実装上の駆動範囲であり、2026-07-30 の実測で判明した通り
物理的な駆動対象パーツは未確定 (下記「頭部ヨー (CH_HEAD) の物理対象」参照)。

## 脚サーボの配線経路

1. 膝サーボ線: femur ウェブの内側に沿わせて股へ
2. 股ピッチ線: coxa 箱枠の配線逃がしから上へ
3. 3 本まとめてスパイラルチューブで束ね、シャーシの φ9 配線穴 ((±16,-6) の 2 穴, v3) から内部へ。下面クレードルのバッテリー線も同じ穴を使う
4. **可動域全域 (股ピッチ -45°〜+55°, 膝 ±44°, ヨー ±40°) で張らない長さ**を
   確保してから束ねる。電源線はサーボ直近でバスへ分岐 (信号のみ PCA へ)

## 腕サーボの配線経路

2026-07-29 固定爪化: 可動グリッパ (旧サブマイクロ×2, palm 後端下から引き出す
配線) は廃止。前腕から先 (claw_mount + 爪ハブ + 指 + 指先チップ) はすべて
受動パーツで配線を持たないため、腕サーボは肩ヨー/肩ピッチ/肘の 3 個のみ
(片腕あたり) で完結する。

1. 肘サーボ線: upper_arm のフレーム内側から肩ブラケットへ
2. 肩ピッチ線と合わせて肩ブラケット背面に沿わせ、シャーシの MICRO 開口
   (肩ヨーサーボの脇) からプレート上面へ引き込む
3. 肩ヨーサーボはシャーシ内蔵 (脚ヨーと同様) なので線はプレート上をそのまま
4. **腕の全可動域 (ヨー ±15°, ピッチ -45°〜85°, 肘 0-95°) で張らない長さ**を
   確保。束ねはヨー回転の根本を避け、シャーシ前縁で 1 点固定

## WS2812B 直列順 (firmware の index と一致)

```
0: メインアイ (背中ポッド前面の Cabin_Eye 裏) → 1-3: 頭部目 ×3 (eye_carrier 裏に取付。
   2026-07-28 以降 index 2 = 中央目は camera_carrier のため未使用/割愛可)
→ 4-7: 赤ランプ大 ×4 → 8-11: 赤ランプ小 ×4
```

頭部の左右目の LED (index 1, 3) は eye_carrier の裏側に貼ると、白い eye_pod
(低インフィル) がバックライトされて回転する瞳ごと光る (任意。省略しても可)。
中央目 (index 2) は固定カメラ目に置換されているため、この LED は結線しない
か省略してよい。

## 音声ユニット (I2S) 配線 — 砲身内蔵マイク+スピーカー (2026-07 追加)

`docs/voice.md` の音声会話ユニット用。INMP441 (I2S マイク) と MAX98357A
(I2S アンプ) は **I2S0 を全二重共有** (firmware `Audio` クラス, 16kHz/16bit/
mono)。BOM #30-33 参照。

| ESP32 ピン | 接続先 | 備考 |
|---|---|---|
| GPIO26 | INMP441 SCK + MAX98357A BCLK | I2S ビットクロック (共有) |
| GPIO25 | INMP441 WS + MAX98357A LRC | I2S ワードセレクト/LRCLK (共有) |
| GPIO27 | MAX98357A DIN | 再生データ (ESP32 → アンプ) |
| GPIO33 | INMP441 SD | 録音データ (マイク → ESP32) |
| 3.3V/GND | INMP441 VDD/GND, **L/R = GND** | L/R を GND に固定 = 左チャンネル出力 |
| 5V/GND | MAX98357A VIN/GND | **GAIN ピンは未結線のままでよい** (既定 9dB)。SD (シャットダウン) ピンも未結線で常時有効 |

- BCLK/WS は 2 デバイスへの分岐配線 (共有バス)。DIN/SD (DOUT/DIN) は
  片方向 1 対 1
- 既存の I2C (GPIO21/22)・DFPlayer UART (GPIO16/17)・WS2812 (GPIO4) と
  ピンの競合なし (GPIO26/25/27/33 はいずれも未使用だった空きピン)
- 配線経路: **MAX98357A は頭部/シャーシ側に搭載**し、砲身内の**スピーカーへ
  スピーカー線 2 本のみ**を Head_Bottom → Mouth_Neck/Ball のボアを通して
  引き出す (I2S 信号線をアンプ〜スピーカー間で引き回さない。ノイズに弱い
  I2S 信号は基板〜アンプ間の短距離のみに留める設計)。**INMP441 は砲身内
  (スピーカーと同じクレードル) に搭載**し、AWG30 の 4 線 (SCK/WS/SD/GND) +
  電源 2 線を同じボアへ通す (BOM #33)
- 半二重運用 (再生中は録音停止) のためマイクとスピーカーの物理的な干渉は
  小さい。マイクの向きは `audio_cradle_mic` の**回転キーで一意に固定**され
  (マイクポート = 砲身下面の φ1.8 開口)、組立時の向き合わせは不要
  (組込み手順は `docs/assembly.md` 参照)。ボアを通る配線は
  **計8芯 (マイク6 + スピーカー2)**

## カメラ電源配線 (2026-07-28 頭部の中央目へ移設, `docs/voice.md`/BOM #34 参照)

**2026-07-28 設計変更**: カメラはポッドのメインアイではなく**頭部の中央目**
(`eye_pod_camera` 裏の `camera_carrier`) に収める。独立 WiFi カメラモジュール
(推奨: Seeed XIAO ESP32S3 Sense) は、**本体の I2C/PCA9685 バスとは一切
接続しない** (信号的に無関係。自前で WiFi 接続し HTTP で静止画/MJPEG を
配信するだけ)。ロジック電源からの給電のみが必要 — **頭部は完全固定 (可動部
なし) なので首の回転部を避ける配慮自体が不要**、電源 2 芯をそのまま頭部内
から胴へ下ろす (音声ユニットのように pod_neck を経由しない)。

| 配線 | 経路 | 備考 |
|---|---|---|
| VCC (5V) | ロジック電源 (BOM #7, 5V/3A DC-DC) → シャーシ 7 タブ間隙間から頭部内へ → camera_carrier 脇の配線切り欠きから XIAO ESP32S3 本体基板の 5V/GND ピンへ | AWG30 シリコン線 2 芯 |
| GND | 同上 | ロジック GND と共通 |

- カメラ子基板 (レンズ側, 20.5x12.5x5.54mm) は `camera_carrier` のポケットへ
  収め、FPC で XIAO ESP32S3 本体基板 (ESP32S3 チップ/WiFi アンテナ/USB-C)
  へ接続する。本体基板自体は `camera_carrier` に載せず、頭部内部の空いた
  スペース (現物合わせ) へ両面テープ等で固定する
- 電流収支の注意は BOM #34 参照 (既存ロジック負荷 ~2.3A + カメラ平均
  0.14A/ピーク0.34A で 5V/3A 定格に対し余裕は縮む — UNVERIFIED, 実測推奨)
- WiFi 接続 (iPhone インターネット共有への STA 参加) の手順は音声ユニットと
  共通。詳細は `docs/voice.md` 「カメラ連携」節参照

## 頭部ヨー (CH_HEAD, ch12) の物理対象 — 2026-07-30 実測で判明した齟齬

**背景**: BOM #2 は「SG90/MG90S ×2 — 頭部ドーム旋回 + 予備」、旧版の想定は
「頭頂の小ドーム (`Head_Dome_Grey`) だけが回転し、軸には既存 `Head_Peg_Upper/
Lower` を流用する」というものだった (firmware `CH_HEAD`=ch12 は既に実装済みで
`servos.writeDeg(CH_HEAD, wz * 25.0f)` により旋回速度 wz に連動して ±25° 振れる)。
本タスクで `Head_Top_Blue`/`Head_Dome_Grey`/`Head_Peg_Upper`/`Head_Peg_Lower` を
実測したところ、**この想定は成り立たないことが判明した**。三系統の独立した
証拠で確認済み:

1. **3MF source_offset フォレンジクス** (`tools/data/kit_assembly_front.json`
   の `Head_Dome_Grey` エントリ, confidence high, bbox-gap 0.00mm, 既に前回
   セッションで確定済みの記録): `Head_Dome_Grey` の `Head_Top_Blue` ローカル
   座標系での位置は `t=(-16.43,-26.47,-9.44)` (@150%) — これは頭部の**前頭部
   (左右の目の間・やや上)** であり、頂点 (crown, 同フレームで概ね `(0,0,+48)`
   付近) からは大きく外れる。同エントリの記述は「完成写真 (`thumbnail_middle.
   png`) で両目の間に見える小さな灰色のリベットと一致」。
2. **完成写真の直接確認** (`~/Downloads/TACHIKOMA.3mf` 同梱
   `Auxiliaries/.thumbnails/thumbnail_middle.png` を本タスクで再取得・拡大
   確認): 前面の顔球体を見ると、両目の間に小さな灰色のドット (`Head_Dome_
   Grey`/`Head_Plug_Grey`) が確かにあるが、頭頂部は完全に滑らかな青いシェル
   で、独立した「ドーム状の可動キャップ」に見える意匠は存在しない。
3. **STL 実測** (本タスク, `model/Head_Dome_Grey.stl` 生メッシュ bbox):
   4.93×5.09×5.35mm (@150%で7.4×7.6×8.0mm) — 非常に小さく、しかも概ね回転
   対称な滑らかなドット形状 (表面にマーキング等の非対称特徴なし) のため、
   **仮に軸回転させても外観上ほぼ判別できない** (回転対称物体を回しても
   見た目が変化しない)。
4. **Head_Peg_Upper/Lower はサイズ的に `Head_Dome_Grey` の軸たり得ない**:
   実測 (生メッシュ, 円柱状の中実ピン, 内部空洞なし) — Upper: 径8.40mm/
   長7.76mm (@150%で径12.6mm/長11.6mm)、Lower: 径9.00mm/長10.05mm (@150%で
   径13.5mm/長15.1mm)。どちらも `Head_Dome_Grey` 自体の最大径 (5.4mm生
   =8.1mm@150%) より太い — 「ドームを貫通/保持する軸ペグ」は幾何的に成立
   しない。
5. **`Head_Peg_Upper/Lower` の実際の役割 (今回新たに特定, 中程度confidence)**:
   `Head_Top_Blue`/`Head_Bottom_Blue` それぞれの鋭角エッジリング検出
   (config.py 既存手法と同一, `face_adjacency_angles>15°` の連結成分) で、
   **両殻の中心軸上・赤道面 (Top⇔Bottom の合わせ目) にほぼ同径の盲穴**が
   見つかった: `Head_Top_Blue` ローカル `(0,0,-32.01)` raw 起点、径9.32mm生
   (14.0mm@150%)・深3.00mm生(4.5mm@150%) と、`Head_Bottom_Blue` ローカル
   `(0,0,+8.46)` raw 起点、径9.25mm生(13.9mm@150%)・深5.00mm生(7.5mm@150%)。
   径がほぼ一致 (14.0mm vs 13.9mm) し、かつ Top/Bottom 両殻の幾何中心軸
   ちょうど (合わせ目の中央) に位置することから、**`Head_Peg_Upper/Lower`
   は上下シェルを内部で軸合わせする通常の組立ダウエルペア** (周囲リムの
   接着に加える中心補強) である可能性が高い — 回転機構ではない。
   なお `Head_Top_Blue` の**真の頂点** (`(0,0,+32.01)` raw) には別の小さな
   同心リング対 (径3.66mm/6.4mm生=5.5mm/9.6mm@150%) が見つかったが、この
   径は `Head_Peg` どちらとも一致せず、`model/*.stl` の全パーツ照合でもこの
   位置に対応する部品は特定できなかった (`Stand_mount_Optional.stl` という
   展示台パーツが別途キットに存在し、こちらの取付穴の可能性がある — 未確認)。

**結論と本タスクでの対応**: `Head_Dome_Grey` を「頭頂の回転ドーム」として
物理マウント (`dome_servo_mount`/`dome_coupler` 等) を新設計する、という
当初の作業前提は実測により棄却される。プロジェクトの確定ルール (README/
CLAUDE.md 鉄則: 可視ジオメトリは元キット形状のみ・独自造形禁止) の下では、
頭頂に「回転させる価値のある」新規ドーム意匠を追加することはこのタスクの
権限を超える (ユーザー判断が必要)。よって **本タスクでは
`hardware/src/make_dome.py` 等の物理マウント実装を行っていない** — CH_HEAD
(ch12) は firmware 上は生きたまま (wz 連動 ±25° 出力) だが、**駆動対象の
実体は未確定**。想定される選択肢 (要ユーザー判断):

- (a) 実測どおり `Head_Dome_Grey` (前頭部の小リベット) をそのまま回転させる
  — 元パーツ流用の原則には合致するが、上記の通り回転対称形状のため見た目の
  効果はほぼゼロで、SG90 (23×12.4×19.5mm) を隠すための頭部内スペースと
  引き換えにする価値が薄い
- (b) CH_HEAD を頭部以外の既存可動要素 (未定) へ再割当てする
- (c) 物理実装を見送り、CH_HEAD を予備チャンネルのまま維持する (BOM #2 の
  SG90 2個のうち1個を予備専用にする)

BOM #2 / docs/shopping.md は「頭部ドーム旋回」という確定済み記述を削除し、
上記の未確定状態を明記する形へ更新した (本タスクの一部)。
